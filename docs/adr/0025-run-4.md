# 0025. `run/4`: the device that answered a request, and whether a cache did

Status: accepted. Changes ADR 0006 (a response says where it was answered) and ADR 0013
(the record's version and the elements `device` and `cached` of `models`)
Date: 2026-11-17
Spec: section 3, "What every run records" (the row "Models"); section 4

## Context

`SPEC.md` section 3 asks the record of every run to say, for every capability request,
the device it was answered on and whether the answer came from a cache. `run/2` and
`run/3` had both fields and held them null: no response of a capability said either
(ADR 0006; `docs/carry-over.md`, the row on the run record's lists, owned by plan 1C,
task P7a). Checkpoint 1C brings the first backend that runs a model, the kind `pack`,
whose worker states its device in each result (ADR 0020, `pack/1`), so the device is
known and can be recorded. ADR 0005 says that every fill of a field after the tag `m1a`
is a new version of the record, and that readers go on reading the versions before.

## Decision

### What a response says (amends ADR 0006)

Every response of a capability (a segmenter's `SegmentResponse`, a filler's `Painted`, a
judge's `Turn`) may say where it was answered: `Served`, made of a device and whether a
cache answered, each of which may be left unsaid (`served_as`; `served`). A response
that says nothing is answered on a device nobody named, from nothing anyone said was a
cache. A device is a name of the protocol's rule for one (`Device`): a lower-case
letter, then lower-case letters, digits, `.`, `_`, `-` and `:`, 32 characters at most
(`cpu`, `mps`, `cuda:0`). The rule holds no path, no space and nothing a terminal obeys.

The handle keeps what an answer it took says, for the run's record, beside how the
request ended. A request that ended without an answer the handle took (a fault, the
handle's own refusal of what came back, a backend that panicked) keeps neither.

**The kind `pack`** says the device its worker's result names and that no cache
answered: the kind has none (`whizbang::pack`).

**The worker's hello** states the device its work runs on while no model is resident:
the pack's core imports no runtime (plan 1C, D10), so `cpu`. A result names the device
of the model that answered it. ADR 0020's rule, that a hello's device may be null while
the worker has not asked its runtime, stands for a worker that cannot say.

### `run/4` (amends ADR 0013)

`run/4` is `run/3` with two fields given values: in each element of `models`,

| Field | Value |
|---|---|
| `device` | The device the answer named, of the rule above, or null when it named none |
| `cached` | `true` or `false` as the answer said, or null when it did not |

Both are null for a request whose `ended` is not `answered`. Nothing else of the shape
changes, so every other rule of ADR 0013 holds of `run/4` as written. The schema is
`crates/whizbang-core/schemas/run-4.json`; what it cannot say, the types refuse: a
device that is not a name of the rule, and a device or a cache on a request that was not
answered. A device that holds a secret the run knows is not kept: it is recorded as not
named. The fixed vector is `served` in `crates/whizbang-core/tests/it/contract/record.rs`
(`record::a_run_4_record_holds_the_device_and_whether_a_cache_answered_for_each_request`).

**What reading does with a `run/3` record.** It is read, and written back as it was, in
its own version: no record is migrated. Its devices and caches are null, which says that
neither is known; one that names either is refused, since no record of that version
could (`record::a_run_3_record_is_still_read_and_says_its_device_is_not_known`). Its
schema is kept beside the new one (`RUN_3_SCHEMA`), and `run/2` is read as before. A
record of any other version is another version, and the refusal now says the three this
build reads.

**What `runs show` prints** of a request: its capability, its backend, model and version
whole (each is at most 128 ASCII characters; a local model's version is its
installation's identity, 71, which a cut at 64 left unable to tell two installations
apart), how it ended, how long it took, `device <name>` or `device not known`, and
`cached`, `not cached` or `cache not known`. "Not known" is not "unknown", which says
that a group of the record was lost (ADR 0013, "What is lost").

### Bounds

A device adds at most 32 characters and a cache 5 to a request's element: with the most
requests a run sends, 1,024, under 40,000 bytes more than ADR 0013's sum at its worst,
inside the room that sum left under the limit of a record
(`record::facts::a_record_with_every_new_list_full_is_under_the_limit_with_the_rest_at_its_worst`,
which now writes every request with the longest device).

## Consequences

- A store keeps `run/3` records and `run/4` records side by side; a reader reads both.
  A store written by this build before the tag `m1c-fakes` may be discarded with the
  version's revert (the plan's "Commit strategy").
- A backend that knows its device says so with one call; one that does not is unchanged.
- Reversing this is a new version of the record.

## Alternatives

- **Migrating `run/3` records to `run/4`.** Turned down: a record is written one way and
  read as it was written; nothing in a `run/3` record would change but its version.
- **A device of any text.** Turned down: a device is printed, and the protocol already
  holds the worker's to a rule.
- **The device in the hello alone.** Turned down: a model's runtime picks its device
  when it loads, so the result, not the hello, says where a request was answered.
